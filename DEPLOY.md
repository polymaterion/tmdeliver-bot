# Обновление бота через GitHub: сначала тест, потом бой

Схема из трёх шагов. Боевой бот не трогаем, пока всё не проверено руками.

```
ваш компьютер ──push──▶ GitHub, ветка freemium ──▶ ТЕСТОВАЯ копия (тестовый бот + тестовый канал)
                                │                              │ ручная проверка по чек-листу (раздел 4)
                                └── Pull Request → merge в main ──▶ БОЕВОЙ сервер: git pull + пересборка
```

Что понадобится: доступ к GitHub-репозиторию бота, SSH на VPS (или Docker на своём компьютере для теста),
Telegram-аккаунт администратора и **второй Telegram-аккаунт** (в роли обычного пользователя — админ и
пользователь в боте видят разные экраны, на одном аккаунте проверить всё честно нельзя).

---

## 1. Залить изменения в GitHub отдельной веткой

Всё делается на вашем компьютере. Меняем **не `main`**, а новую ветку `freemium` — боевой код остаётся нетронутым.

```bash
# если репозитория ещё нет на компьютере
git clone https://github.com/ИМЯ/РЕПО.git tmdeliverbot
cd tmdeliverbot
git checkout main && git pull

# новая ветка
git checkout -b freemium
```

Распакуйте архив `tmdeliver-bot-freemium.zip` и скопируйте его содержимое в папку репозитория **с заменой файлов**
(новые файлы: `billing.py`, `DEPLOY.md`, `tests/`, `pytest.ini`, `requirements-dev.txt`; изменены: `main.py`,
`locales.py`, `docker-compose.yml`, `.env.example`, `README.md`).

Проверьте, что в коммит не попадут секреты:

```bash
git status                  # в списке не должно быть .env
git diff --stat
git add -A
git commit -m "Freemium: баланс публикаций, оплата переводом, ручная очередь публикации"
git push -u origin freemium
```

> Если `git status` показал `.env` — остановитесь и не делайте `git add`: файл должен быть в `.gitignore`.

## 2. Тестовый бот и тестовый канал

1. **Тестовый бот.** В [@BotFather](https://t.me/BotFather): `/newbot` → имя, например `TM Deliver TEST`, username `…_test_bot`.
   Сохраните токен. Боевой токен никуда не копируйте: два бота на одном токене будут воевать за обновления
   (ошибка `Conflict: terminated by other getUpdates request`).
2. **Тестовый канал.** Создайте канал (можно приватный), например «TM Deliver TEST».
   Добавьте тестового бота **администратором** с правом «Публикация сообщений» (и «Редактирование/удаление
   сообщений», если бот будет их менять).
3. **ID канала.**
   - Публичный канал: `CHANNEL_ID=@username_канала`.
   - Приватный: опубликуйте любой пост в канале, затем откройте в браузере
     `https://api.telegram.org/bot<ТЕСТОВЫЙ_ТОКЕН>/getUpdates` — найдите `"chat":{"id":-100…` и возьмите это число.
     (Если список пуст — напишите пост ещё раз, убедитесь что бот админ.)
4. **Ваш ID** (для `ADMIN_IDS`) — у [@userinfobot](https://t.me/userinfobot).
5. **Второй аккаунт** («пользователь»): подпишите его на **тестовый канал** — бот проверяет подписку на `CHANNEL_ID`,
   без неё дальше экрана «Подпишитесь» не пустит.
6. (Необязательно) тестовая группа, если проверяете публикацию в группы: добавьте туда тестового бота.

## 3. Запуск тестовой копии

Вариант **А — на том же VPS**, в отдельной папке (рядом с боевой, имена контейнеров, сети и тома БД разные).
Вариант **Б — на своём компьютере** с Docker Desktop (команды те же, `STACK_NAME` можно не задавать).

```bash
# на VPS (вариант А); боевая папка ~/tmdeliverbot не трогается
cd ~
git clone -b freemium https://github.com/ИМЯ/РЕПО.git tmdeliverbot-test
cd tmdeliverbot-test
cp .env.example .env
nano .env
```

Заполните `.env` **тестовыми** значениями:

```ini
BOT_TOKEN=токен_ТЕСТОВОГО_бота
ADMIN_IDS=ваш_id
CHANNEL_ID=-100…или@тестовый_канал
BOT_URL=https://t.me/ваш_тестовый_бот
TZ_OFFSET=3
POSTGRES_PASSWORD=любой_длинный_пароль          # openssl rand -base64 24
CARD_NUMBER=0000 0000 0000 0000                 # заведомо фиктивная карта
CARD_HOLDER=ТЕСТ

# разделяет тест и бой на одном сервере — ОБЯЗАТЕЛЬНО для варианта А
STACK_NAME=tmdeliverbot_test
COMPOSE_PROJECT_NAME=tmdeliverbot_test
```

**Проверка до запуска (вариант А, важно):** убедитесь, что тест не заденет боевые контейнеры.

```bash
docker compose config | head -3        # первая строка должна быть: name: tmdeliverbot_test
docker compose ps                      # пока пусто — боевые контейнеры здесь не видны
```

Если вместо `tmdeliverbot_test` видите `tmdeliverbot` — **не запускайте**, проверьте `.env`.

Запуск и логи:

```bash
docker compose up -d --build
docker compose logs -f bot            # ждём строку про запуск polling, без Traceback
```

Автотесты логики (по желанию, не требуют Telegram): `pip install -r requirements-dev.txt && pytest -q tests`.

### Полезно знать при тестировании

- **Время.** 24 часа и сроки объявлений ждать не нужно — сдвигайте даты в БД
  (`docker compose exec db psql -U tmdeliverbot -d tmdeliverbot`):

  ```sql
  -- «последняя публикация была 25 часов назад» (снять 24-часовое ограничение)
  UPDATE drafts SET published_at = published_at - interval '25 hours' WHERE user_id = <ID_ПОЛЬЗОВАТЕЛЯ> AND status = 'published';
  -- «поездка уже прошла» для открытого объявления
  UPDATE drafts SET travel_date = to_char(now() - interval '2 days', 'DD.MM.YYYY') WHERE id = <ID_ЗАЯВКИ>;
  -- «бесплатная публикация истекла»
  UPDATE drafts SET travel_date = to_char(now() - interval '2 days', 'DD.MM.YYYY') WHERE user_id = <ID> AND status = 'published' AND ad_type = 'carrier';
  -- баланс и история
  SELECT * FROM user_balances; SELECT * FROM balance_ledger ORDER BY id DESC LIMIT 20;
  SELECT id, user_id, status, funding, published_at FROM drafts ORDER BY id DESC LIMIT 20;
  ```
- **Заявки на оплату** — реквизиты показываются из `CARD_NUMBER`; платить по-настоящему не нужно:
  отправьте любое фото как «чек» и подтвердите его с админского аккаунта.
- Админские команды: `/queue`, `/balance <id>`, `/history <id>`, `/credit <id> N причина`, `/adjust <id> ±N причина`, `/users`.

## 4. Ручной чек-лист (отметьте каждый пункт)

Обозначения: **П** — второй аккаунт (пользователь), **А** — ваш админский аккаунт.

**Бесплатная публикация и очередь**
- [ ] П: `/start` → создать объявление → «отправлено на проверку». Баланс 0 (`/balance`).
- [ ] А: пришло уведомление с кнопками «Одобрить / Отклонить». Нажать «Одобрить» → в канале **ничего не появилось**; кнопки сменились на «📢 Опубликовать / Отложить / Отклонить»; П получил «одобрено».
- [ ] П: пока заявка в работе, пытается создать второе объявление (кнопка «Создать объявление», повторный `/start`, повторное нажатие «Подтвердить») → везде сообщение «⏳ У вас уже есть объявление…» с «Посмотреть статус / Отмена».
- [ ] П: «Посмотреть статус» показывает статус; «Отменить объявление» отменяет, после этого можно создать новое.
- [ ] А: «📢 Опубликовать» → пост в канале; П получил «опубликовано». Дважды быстро нажать «Опубликовать» (или нажать на старой копии сообщения) → второго поста нет.
- [ ] П: после публикации сразу создать второе объявление, А одобряет и жмёт «Опубликовать» → «⏳ Пока нельзя опубликовать…» с датами последней и следующей публикации.
- [ ] Сдвинуть время (SQL выше, −25 ч) → теперь публикуется (если у П есть платная публикация или бесплатная освободилась; иначе см. ниже).

**Оплата**
- [ ] П: «💳 Дополнительные публикации» → «5 публикаций — 200 ₽». Если открытое объявление с поездкой через ~3 дня — **до** реквизитов приходит предупреждение «⚠️ До вашей поездки осталось 3 дня…» с кнопками «Купить / Выбрать другой пакет / Отмена»; покупку можно продолжить.
- [ ] Реквизиты: показан номер из `CARD_NUMBER`, номер заявки, сумма. А получил «Новая заявка на оплату».
- [ ] П: отправляет фото (затем отдельно — файл/документ) как чек → А получает чек с данными пользователя, пакетом, суммой и кнопками «Подтвердить оплату / Отклонить чек». Баланс П пока 0.
- [ ] А: «❌ Отклонить чек» → П получает сообщение с кнопками «Отправить чек повторно / Новая заявка»; баланс 0. П отправляет чек снова → А подтверждает → баланс +5, П уведомлён.
- [ ] А: повторно жмёт «Подтвердить» на той же заявке → «Уже подтверждено», баланс не вырос (`/balance <id>`).
- [ ] После подтверждения оплаты объявление в канал **не ушло** само.
- [ ] Платная публикация: у П занято бесплатное место → одобренное объявление → «Опубликовать» → пост в канале, баланс −1 ровно (`/history <id>` показывает списание).
- [ ] Бесплатная публикация (свободное место) → платный баланс не изменился.
- [ ] У П баланс 5: 5 объявлений подряд не публикуются (1 в 24 ч), остальные ждут.
- [ ] Платное объявление без баланса: одобрено → «Опубликовать» → отказ «оплата не подтверждена / нет публикаций»; П видит «ожидает оплаты» и кнопку покупки.
- [ ] Отклонить оплаченное объявление → баланс П не изменился; П получил текст «купленные публикации сохранены».

**Ошибки и устойчивость**
- [ ] Ошибка Telegram: временно снимите у тестового бота право публикации в канале → А жмёт «Опубликовать» → «❌ Ошибка публикации», баланс не списан, объявление не «опубликовано». Верните права → «Опубликовать» снова → успех, списано ровно 1.
- [ ] Дата поездки в прошлом (SQL выше) → «Опубликовать» не публикует, объявление отменяется, П получает предложение создать новое; в «Купить» для такого объявления оплата не предлагается.
- [ ] Перезапуск: `docker compose restart bot` и отдельно `docker compose down && docker compose up -d` (**не** `down -v` — он удалит базу) → баланс, заявки на оплату, статусы объявлений на месте; бесплатная публикация повторно не выдалась.
- [ ] Две админки одновременно (если есть второй админ): одновременное «Подтвердить»/«Опубликовать» → одно начисление / один пост.
- [ ] Ручные операции: `/credit <id> 2 тест` и `/adjust <id> -1 ошибка` → видны в `/history <id>`; без причины команда отказывает.
- [ ] `/users` присылает CSV; заблокируйте тестового бота вторым аккаунтом → в `/users` счётчик «заблокировали» вырос.
- [ ] Туркменский язык: переключить язык у П и пройти экраны покупки и статуса.

Если хоть один пункт не прошёл — **на бой не обновляем**: исправляем в ветке `freemium`, `git push`, на тестовом сервере `git pull && docker compose up -d --build`, повторяем проверку.

## 5. Проверка миграции на копии боевой базы (рекомендуется)

Обновление меняет схему боевой БД (новые колонки статусов, таблицы платежей и баланса, уникальный индекс «одно
активное объявление на пользователя»). Чтобы убедиться, что на **реальных данных** всё проходит, прогоните его на копии.

```bash
# 1. На БОЕВОМ сервере: дамп (только чтение, бота не останавливает)
cd ~/tmdeliverbot
docker compose exec -T db pg_dump -U tmdeliverbot tmdeliverbot > ~/prod_copy.sql

# 2. В тестовой папке: поднять ТОЛЬКО базу, залить дамп
cd ~/tmdeliverbot-test
docker compose down -v          # здесь -v допустим: сносим ТЕСТОВУЮ базу (проверьте, что вы в тестовой папке!)
docker compose up -d db
sleep 10
cat ~/prod_copy.sql | docker compose exec -T db psql -U tmdeliverbot -d tmdeliverbot

# 3. Перед запуском бота обезопасить копию: не публиковать старые «отложенные» объявления в тестовый канал
docker compose exec db psql -U tmdeliverbot -d tmdeliverbot -c "UPDATE drafts SET scheduled_at = NULL;"

# 4. Запустить бота (миграция выполнится при старте)
docker compose up -d --build
docker compose logs --tail 50 bot
```

Проверить результат:

```sql
SELECT status, funding, count(*) FROM drafts GROUP BY 1,2 ORDER BY 1,2;
-- опубликованные старые объявления → published/free (они занимают бесплатное место до истечения)
-- не должно быть пользователей с двумя активными заявками:
SELECT user_id, count(*) FROM drafts WHERE status IN ('pending','approved','publishing','publish_error') GROUP BY 1 HAVING count(*) > 1;
```

Что произойдёт с данными при миграции (знайте заранее):
- опубликованные ранее объявления → `published`, бесплатное место занято до окончания их срока (иначе обновление «выдало» бы бесплатную публикацию поверх активной);
- ранее отложенные (`scheduled_at`) → `approved`;
- неопубликованные старше 7 дней → `rejected` (раньше «отклонено» нигде не хранилось), свежие → `pending`;
- если у пользователя было несколько открытых заявок — остаётся самая новая, остальные → `cancelled`.

> На копии **не запускайте рассылки** — в ней настоящие пользователи, а тестовый бот им ничего не отправит, но
> лишние ошибки в логах будут. Тестируйте со своими двумя аккаунтами.

## 6. Обновление боевого бота

Только после того, как чек-лист из раздела 4 (и по возможности раздел 5) пройден полностью.

### 6.1. Подготовка (боевой сервер)

```bash
ssh пользователь@адрес_vps
cd ~/tmdeliverbot

# запомнить текущую версию кода — по ней откатываемся
git rev-parse --short HEAD            # запишите хэш

# бэкап базы (обязательно: миграция схемы необратима без бэкапа)
docker compose exec -T db pg_dump -U tmdeliverbot tmdeliverbot > ~/backup_before_freemium_$(date +%Y%m%d_%H%M%S).sql
ls -la ~/backup_before_freemium_*.sql  # файл не должен быть пустым

# добавить настройки оплаты в боевой .env
nano .env
#   CARD_NUMBER=реальный_номер_карты
#   CARD_HOLDER=имя_получателя      # необязательно
# STACK_NAME и COMPOSE_PROJECT_NAME на бою НЕ задавать — имена контейнеров останутся прежними
```

Лучшее время — когда мало активных заявок. Старые сообщения админу о заявках, пришедшие до обновления, содержат
старые кнопки; после обновления все ожидающие заявки доступны через **`/queue`** (с кнопками «Одобрить» /
«📢 Опубликовать»). Либо заранее разберите очередь вручную.

### 6.2. Вывести изменения в `main` через Pull Request

На GitHub: **Pull requests → New pull request**, base `main` ← compare `freemium` → проверьте список изменённых
файлов (не должно быть `.env`) → **Create pull request → Merge pull request**.

(Из консоли то же самое: `git checkout main && git merge freemium && git push` — но через PR вы видите, что именно
уходит в бой, и остаётся история.)

### 6.3. Обновить сервер

```bash
cd ~/tmdeliverbot
git pull                              # должен подтянуться merge с freemium
docker compose up -d --build          # пересобрать образ и перезапустить бота; БД и данные сохраняются
docker compose ps                     # оба контейнера Up (db — healthy)
docker compose logs --tail 100 bot    # нет Traceback; миграция выполнилась молча
```

Если `git pull` ругается на локальные изменения: `git status`, затем `git stash` (или обсудите, что менялось на сервере руками)
и повторите `git pull`.

### 6.4. Быстрая проверка на бою (5 минут)

- [ ] Бот отвечает на `/start` с обычного аккаунта; `/buy` показывает реквизиты **боевой** карты.
- [ ] `/queue` (админ) показывает ожидающие заявки; `/users` присылает CSV.
- [ ] Одно реальное объявление проходит путь: создать → «Одобрить» → «📢 Опубликовать» → пост появился в боевом канале.
- [ ] `docker compose logs --tail 100 bot` — без ошибок.

### 6.5. Откат, если что-то пошло не так

Только код (данные остаются новые; старый код с новой схемой в основном работает, но для надёжности лучше полный откат):

```bash
cd ~/tmdeliverbot
git reset --hard <хэш_из_шага_6.1>
docker compose up -d --build
```

Полный откат с данными (потеряются изменения в БД после бэкапа — оплаты, балансы, новые заявки):

```bash
docker compose stop bot
docker compose exec -T db psql -U tmdeliverbot -d postgres -c "DROP DATABASE tmdeliverbot;" -c "CREATE DATABASE tmdeliverbot OWNER tmdeliverbot;"
cat ~/backup_before_freemium_ДАТА.sql | docker compose exec -T db psql -U tmdeliverbot -d tmdeliverbot
git reset --hard <хэш> && docker compose up -d --build
```

## 7. Типичные проблемы

| Симптом | Причина / решение |
|---|---|
| `Conflict: terminated by other getUpdates request` | Два запущенных бота на одном токене. У теста и боя должны быть **разные** токены; проверьте `docker ps`. |
| Бот не публикует: `chat not found` / `Forbidden` / `not enough rights` | Неверный `CHANNEL_ID` или бот не администратор канала с правом публикации. |
| Тестовый пользователь застрял на «Подпишитесь на канал» | Подпишите второй аккаунт на **тестовый** канал. |
| `docker compose config` показывает `name: tmdeliverbot` в тестовой папке | В `.env` теста не заданы `STACK_NAME`/`COMPOSE_PROJECT_NAME`. Не запускайте, пока не исправите — иначе команды затронут боевые контейнеры. |
| Реквизиты не показываются: «временно не настроены» | Пустой `CARD_NUMBER` в `.env`; после правки — `docker compose up -d --force-recreate bot`. |
| `permission denied` при `docker` | Пользователь не в группе `docker`: `sudo usermod -aG docker $USER` и перезайти по SSH. |
| Нужно «стереть» тестовую базу и начать заново | **Только в тестовой папке:** `docker compose down -v`. Никогда не выполняйте `down -v` в боевой папке. |

## 8. Дальнейшая работа

Для каждого следующего изменения: новая ветка → `git push` → `git pull` + пересборка в тестовой папке → проверка → PR в
`main` → `git pull` + `docker compose up -d --build` на боевом сервере (с бэкапом БД перед обновлением).
